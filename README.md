# Guider

웹 페이지 사용법을 AI가 안내해주는 크롬 익스텐션 프로젝트입니다.

이 레포지토리는 **모노레포** 구조로 관리되며, 크롬 익스텐션 본체(`extension`)와 API 프록시 서버(`server`)를 하나의 저장소에서 함께 관리합니다.

---

## 폴더 구조

```
Guider/
├── extension/                 # 크롬 익스텐션 본체
│   ├── manifest.json          # 익스텐션 설정 파일
│   ├── background/            # Service Worker (탭 관리, 캐시)
│   ├── content/               # Content Script (DOM 파싱, 하이라이트)
│   ├── sidepanel/             # 사이드바 UI (HTML/CSS/JS)
│   ├── ai/                    # AI 연동 (API 호출, 프롬프트 관리)
│   └── assets/                # 아이콘, 이미지 등 정적 파일
├── server/                    # API 키 보호용 프록시 서버
├── docs/                      # 요구사항 정의서, 회의록 등 문서
└── README.md
```

---

## 브랜치 규칙

| 브랜치           | 용도                  |
| ---------------- | --------------------- |
| `main`           | 배포 가능한 안정 버전 |
| `develop`        | 통합 개발 브랜치      |
| `feat/[기능명]`  | 새로운 기능 개발      |
| `fix/[버그명]`   | 버그 수정             |
| `chore/[작업명]` | 빌드, 설정, 기타 잡무 |
| `docs/[문서명]`  | 문서 작업             |

**브랜치 생성 규칙**

- 모든 작업은 `develop` 브랜치에서 분기합니다.
- 브랜치 이름은 소문자와 하이픈(`-`)을 사용합니다. (예: `feat/dom-parser`)
- 작업 완료 후 `develop`으로 PR을 올립니다.
- `main` 브랜치에는 직접 푸시하지 않습니다.
- PR 승인 후 해당 브랜치 및 작업 완료한 브랜치는 삭제합니다.

---

## PR 규칙

- **1명 이상의 승인(Approve)** 을 받아야 머지할 수 있습니다.
- PR 제목은 브랜치 이름과 동일한 형식으로 작성합니다. (예: `[feat] DOM 파서 구현`)
- PR 본문에는 **작업 내용 / 변경 이유 / 테스트 방법** 을 간략히 작성합니다.
- 리뷰어는 코드 리뷰 후 승인 또는 변경 요청을 남깁니다.
- Merge 방식은 **Squash and Merge** 를 기본으로 합니다.
